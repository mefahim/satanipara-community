## 0. What changed vs the foundation report §8.4 (read first)

§8.4's draft privileges are **superseded** by the matrix below. Do not

| §8.4 said | Correct (this document) | Why |
|---|---|---|
| App user: SELECT, INSERT, UPDATE, **DELETE** on the database | App user: SELECT, INSERT, UPDATE on `ledger_entries` / `ledger_reversals`, **no DELETE** anywhere on those tables; SELECT, INSERT only on `activity_log`; SELECT, UPDATE only on `sequences`; full DML only on ordinary tables | The ledger is append-only (Doc 06 §7.1). | Backup user: SELECT, LOCK TABLES | Backup user: SELECT, LOCK TABLES, **SHOW VIEW, EVENT, TRIGGER** | `mysqldump --routines --triggers` needs the last three; without them the dump silently omits triggers/views/events. |

## 4. Apply the exact grants (phpMyAdmin → SQL)

hPanel's privilege checkboxes cannot express this model (per-table
grants for the app user; column-level grants for the reporting user).
The exact grants live in **`identities.sql`** (in the Worker C
work folder — the coordinator will hand you the file, or it ships with
the Phase 1 handover). Apply them as follows:

1. hPanel → **Databases** → **phpMyAdmin** (or **Advanced →
   phpMyAdmin**). Log in — phpMyAdmin on shared hosting logs you in as
   the account's database admin.
2. Click the **SQL** tab.
3. Paste the contents of `identities.sql` **after replacing each
   `<VAULT:…>` placeholder with the real password from the secure vault**
   (four placeholders: `satanipara-db-app`, `satanipara-db-mig`,
   `satanipara-db-bkp`, `satanipara-db-rep`). **Do not save the file
   with real passwords in it** — paste from the vault, run, and close
   without saving.
4. Click **Go**. Expected: no errors.
   - The file starts with `DROP USER IF EXISTS …` + `CREATE USER …`
     for the four users — this is intentional: it replaces the
     hPanel-created users with the exact definitions. (If you would
     rather keep the hPanel-created users and only fix their grants,
     delete the `DROP USER` / `CREATE USER` lines and run only the
     `GRANT` / `REVOKE` / `FLUSH PRIVILEGES` part — but then the
     passwords stay as the ones you set in step 3, and the vault
     entries must match those.)
   - **The `REVOKE` block at the end is remediation-only.** If it
     reports `ERROR 1141 (42000): There is no such grant defined`,
     that means "already tight" — not a failure. Re-run that block with
     `--force` semantics (phpMyAdmin: tick "Enable foreign key checks"
     is unrelated; simply ignore 1141 lines) or skip it on a fresh
     install where the grants were never widened.
5. **Reporting user, column-level grant — read carefully.** The
   `GRANT SELECT (id, name_bn, name_en, member_no, member_type,
   status, created_at) ON u263467780_satina6para86.users TO
   'u263467780_satina6para86_rep'@'127.0.0.1'` line runs in phpMyAdmin
   SQL exactly as written. **If it errors** (for example because the
   `users` table does not exist yet — the migrations have not run):
   do **not** fall back to a table-level `GRANT SELECT ON users`.
   Omit the reporting user's `users` grant entirely and re-run that
   one line after the migrations have created the table. A reporting
   user with no `users` access is safe; one with full `users` access
   exposes password hashes and encrypted phones.
6. Verify with the `SHOW GRANTS` block at the end of `identities.sql`
   (run those four statements in the SQL tab). Expected:
   - `app`: `USAGE on *.*`, then per-table grants; **no** `DELETE` on
     `ledger_entries` / `ledger_reversals` / `activity_log`; **no** DDL
     privilege anywhere.
   - `mig`: the DDL+DML set on `u263467780_satina6para86.*` only; no `*.*`
     grant, no `GRANT OPTION`.
   - `bkp`: `SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER` on the
     database only.
   - `rep`: `SELECT` on the four finance tables + the column list on
     `users` (or no `users` grant at all, per step 5).

## 7. Password policy + rotation (standing rules for these four users)

- **Generation:** random, ≥ 32 characters, unique per user, generated
  by the vault/hPanel generator — never a memorable word, never reused
  from another account.
- **Storage:** secure vault only. No password in chat, email, a doc, a
  screenshot, `.env` history, or a shell history file.
- **Host restriction:** all four users are `'127.0.0.1'` only — no `%`
  (any host). The application, the deploy pipeline, and the backup job
  all run on the same host, so no remote database user is needed. If a
  future need arises for a remote user, that is a new decision, not an
  edit to these users.
- **Rotation (every 90 days, or immediately if a password is ever
  exposed):** (1) generate a new password in the vault; (2) apply it
  with `ALTER USER 'u263467780_satina6para86_<role>'@'127.0.0.1'
  IDENTIFIED BY '<new>'; FLUSH PRIVILEGES;` from phpMyAdmin SQL;
  (3) update the place that uses it (`.env` for `app`; deploy pipeline
  secret for `mig`; backup job for `bkp`); (4) verify the service still
  connects; (5) only then consider the old password dead. Rotate one
  user at a time, never all four at once.
- **Expiry enforcement:** MariaDB supports `ALTER USER …
  PASSWORD EXPIRE INTERVAL 90 DAY`, but on Hostinger shared hosting
  the account may not permit it — if the statement errors, enforce the
  90-day rotation procedurally (calendar reminder) instead. There is no
  `validate_password` plugin on shared hosting, so password *quality*
  is enforced by the generation rule above, not by the server.
- **Lockout:** failed-login lockout (`FAILED_LOGIN_ATTEMPTS` /
  `PASSWORD_LOCK_TIME`) is not configurable on shared hosting; rely on
  hPanel's brute-force protection and on the fact that the users are
  `127.0.0.1`-only.
- **No password in the repo, ever.** The `.env` on the server holds the
  app password (mode 600, outside the document root, as the foundation
  report verified). The migration password lives only in the deploy
  pipeline secret store, never on the app server at runtime.
